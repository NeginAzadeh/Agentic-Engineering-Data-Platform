# AI Agent foundations: bounded data tools

## What a tool and function call mean

A tool is an ordinary program function with a defined purpose, inputs, and output. Our tools retrieve facts from the local warehouse. They are useful now, without an AI model.

The local Ollama Agent now receives descriptions and JSON schemas for these operations. Instead of writing SQL, it proposes a function name and structured arguments, for example:

```json
{
  "name": "list_stale_open_prs",
  "arguments": {
    "repository": "dbt-labs/dbt-core",
    "min_age_days": 7,
    "limit": 5
  }
}
```

The application, not the model, decides whether to execute it. `AgentTools.call_tool` checks the name against an allowlist, checks exact argument names, and invokes a function whose runtime validation checks values. The function executes fixed read-only queries. Its JSON-compatible result is returned to the model as untrusted evidence by the new bounded loop. The data tools themselves remain independent of models; see [the local Agent guide](local_agent.md).

## Available operations

| Tool | Returns |
| --- | --- |
| `get_repository_kpis(repository)` | Existing observed-cohort metrics, definitions, and source context |
| `list_stale_open_prs(repository, min_age_days, limit)` | Oldest matching observed-open PRs, their extraction-based ages, timestamps, run IDs, and GitHub references |
| `get_pr_details(repository, pr_number)` | Stored title, state, author, lifecycle dates, observation time, source URL, and pagination/error provenance |
| `get_data_quality_status(repository)` | Freshness, latest ingestion attempt, contributing observation runs, completeness, source errors, rejected counts, and quality warnings |

KPI formulas reuse the existing checked-in analytics SQL. They are not regenerated by a model. Merge rate is a fraction; merge durations are hours and open ages are days. Sample counts and null values retain the existing semantics.

## Input policy and schemas

`tool_schemas.py` exports four provider-neutral objects containing `name`, `description`, and a JSON Schema `parameters` object. Every argument is required and `additionalProperties` is false. A future provider adapter can wrap these definitions in its own API format. The schemas describe the contract; runtime checks enforce it independently without a model SDK or JSON Schema dependency.

- Repository: GitHub `owner/name`, ASCII owner/name characters, owner length up to 39, repository name length up to 100. URLs, quotes, whitespace, extra slashes, and dot-only repository names are rejected. Names are normalized to lowercase. Validation checks syntax, not existence or current visibility on GitHub.
- PR number: actual Python integer from 1 through DuckDB's positive BIGINT maximum. Booleans, floats, and strings are rejected.
- Age threshold: finite integer/float from 0 through 36500 days. Booleans, strings, NaN, infinity, and negative values are rejected.
- Limit: actual integer from 1 through 100. At most that many PRs are returned; one extra row is queried to compute `has_more`.

List filtering uses `age >= min_age_days`. This inclusive minimum is distinct from the existing `open_prs_older_than_7_days` KPI, which uses `age > 7`. Both are explicitly documented; neither silently rounds days or uses current time.

Only the four schema names are dispatched. `execute_sql`, private method names, SQL text, and extra arguments such as database paths are rejected. Unknown repository/PR identifiers are looked up in local observations, not checked on GitHub.

## Parameterized SQL and read-only access

Queries keep executable SQL separate from supplied values:

```python
connection.execute(
    "SELECT * FROM pull_requests WHERE repository = ? AND pr_number = ?",
    [repository, pr_number],
)
```

The `?` placeholders bind values as data. A string resembling SQL cannot become part of the query's syntax. Input validation provides useful constraints; parameter binding remains the query boundary. See [DuckDB's Python DB API documentation](https://duckdb.org/docs/current/clients/python/dbapi).

Every input-based filter and limit uses bound parameters. The only SQL text concatenation wraps an existing, trusted, checked-in KPI query in a session-local view; it never includes user input. SQL and database paths are not tool arguments. The internal Python helpers are trusted application code, not tools advertised to the model.

Calls open `duckdb.connect(..., read_only=True)`, use UTC and a transaction, and close the connection. Temporary views exist only in that session. Missing databases are reported rather than created. No raw files, database tables, reports, or existing pipeline functions are changed. All tool outputs are JSON-compatible; timestamps are UTC strings and unavailable values are null.

## Evidence, freshness, and limitations

Successful responses contain `tool`, `repository`, `status`, `data`, `evidence`, and `limitations`. Evidence includes the warehouse name, repository reference, checked-at timestamp, PR extraction range, supplying run IDs, and data-quality context.

Per-PR age uses that PR's `source_extracted_at`, including when retained from an earlier snapshot. A PR observed open may have closed since extraction. Every response sets `github_live_status_verified` to false. Constructed links such as `https://github.com/owner/repo/pull/123` identify supporting PRs but do not imply that their current contents were fetched.

Source freshness uses elapsed hours between the tool's UTC check time and source extraction timestamps. The explicit local policy marks data stale only when more than 24 hours old; exactly 24 hours is not stale. The response reports the threshold and check time. This is a starting policy, not a business SLA or a claim of pipeline malfunction.

Freshness includes the latest extraction attempt's age, oldest/newest PR observation ages, and number of stale PR observations. A recent failed attempt does not establish fresh PR data: its error and older observation ages remain visible. Negative latest-extraction age is unknown and flagged as a future timestamp. Observation-based ages/KPIs remain unchanged when only the check time changes.

Quality context includes both the latest run and runs supplying retained PRs. Earlier rejected records and issues remain visible after a later clean run. Warnings identify incomplete/unknown pagination, missing provenance, ingestion errors, rejected records, stored quality issues, stale observations, mixed observation times, or unavailable duration inputs. These warnings describe evidence; they do not invent causes.

The latest run and each contributing run now expose stored `pages_fetched`, `pagination_complete`, `stop_reason`, and `source_start_url`. The original `source_url` remains available for compatibility; the explicit new name identifies the initial API request URL. Its `page` parameter is not a page-count or completeness measurement. A missing stored page count remains `null`, even if the URL contains a page number. No analytics SQL or warehouse contents change.

Freshness explicitly labels its unit as hours and explains that `stale_pr_observation_count` includes all PR states. An old cached observation is not necessarily an old or open PR, and says nothing about later GitHub changes. The Agent's Python formatter renders checked-at extraction age in hours and days using these existing values; the data tools themselves still return the original numerical hour fields. This keeps evaluation reference reads comparable without introducing another independently changing clock.

Direct tools and evaluation records retain full evidence. Only the Agent's model-facing presentation omits numerical extraction ages, the per-result `stale_after_hours` policy threshold, check timestamps, and API starting URLs, explicitly explaining that Python owns their display. Evidence is not deleted from the warehouse or replaced with `null`; the full returned results still support evaluation and deterministic rendering. The model continues to receive extraction times, page counts, completeness, stop reason, warnings, PR links/fields, and KPI values. Python displays the actual age and policy threshold separately, preventing the per-result threshold from being copied as an actual age. Guards still reject ambiguous numerical ages and unsupported state-change claims.

A future Agent should state observation times, cite returned run IDs and PR links, and disclose completeness and quality warnings before interpreting metrics. It may propose further investigation, but these inputs cannot support invented review activity, bottleneck root causes, or developer-performance conclusions. Titles and other source text may contain malicious instructions: treat them as untrusted quoted data, never commands or authority. The model integration must preserve this separation.

## Results and errors

- `status: ok`: successful operation, including a known repository with zero matching PRs.
- `status: not_found`: no matching local repository/PR observation. It does not establish nonexistence or absence on GitHub.
- `status: error`: invalid call, missing warehouse, or unreadable expected warehouse data. Error details are structured and do not expose executable SQL or internal database error text.

`call_tool` returns structured errors for invalid proposals. Direct Python methods/functions raise `ValueError` for invalid arguments, following ordinary Python conventions; use the dispatcher as the future model boundary. Valid tool calls return structured results in either style. Low-level application path/clock configuration is not exposed to model calls.

From PowerShell in the project root:

```powershell
.\.venv\Scripts\python.exe -c "import json; from src.engineering_intelligence.agent_tools import AgentTools; print(json.dumps(AgentTools().call_tool('list_stale_open_prs', {'repository': 'dbt-labs/dbt-core', 'min_age_days': 7, 'limit': 5}), indent=2))"
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

For other calls, open `.\.venv\Scripts\python.exe` interactively:

```python
import json
from src.engineering_intelligence.agent_tools import AgentTools
from src.engineering_intelligence.tool_schemas import TOOL_SCHEMAS

tools = AgentTools()
print(json.dumps(tools.get_repository_kpis("dbt-labs/dbt-core"), indent=2))
print(json.dumps(tools.get_pr_details("dbt-labs/dbt-core", 16690), indent=2))
print(json.dumps(tools.get_data_quality_status("apache/airflow"), indent=2))
print(json.dumps(TOOL_SCHEMAS, indent=2))
```

The tools use the already-installed DuckDB dependency and Python standard library. Direct tool calls still make no network or model calls and need no API keys, billing account, paid service, local model, or new packages. The separately implemented local Agent calls the installed Ollama model over loopback using existing `requests`.

Tests use isolated temporary warehouses and a controlled freshness clock. They cover all four tools, matching existing KPIs, argument limits, schema metadata, parameter binding, blocked SQL/private operations, empty/missing results, incomplete and stale data, earlier quality warnings, future extraction times, strict JSON, and unchanged database bytes under read-only calls. The existing ingestion, warehouse, and analytics suites also run.
